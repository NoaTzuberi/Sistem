Date: 2026-10-08
Scope: docs/BUILD_PLAN.md Phase 13a (PRD §5.6): the coach's food list, the per-coach nutrition config and calorie
suggestion, one nutrition plan per trainee (draft → publish → versions), nutrition templates, the trainee's
Nutrition tab with swap lists, coach mode (read-only), the new onboarding "Nutrition preferences" step, the

================================================================================
1. SUMMARY
================================================================================
- Food list (coach): exchange-list items per group (protein / carb / fat / vegetable): name and portion as she
  writes them, optional grams, optional kcal (never above the group value), a "new" tag, diet tags. Used items are
  archived (they keep resolving), unused ones deleted. Seeded from the guide: 44 items + the "1,500" template.
- Calorie suggestion in one pure module (calorieTarget.ts, reused by 13c): Mifflin-St Jeor (latest weigh-in, else
  the onboarding weight) × activity factor (training days) → goal %. Sex other / missing → the coach picks the
  formula or types the target. All numbers in ONE config (nutrition.config.ts) + the coach's own overrides
  (Dashboard → Nutrition → Settings). Floor 1,200: below it publishing needs her explicit confirmation of that
  exact target (stored, enforced on publish).
- Nutrition plan: one autosaved working copy per trainee (coach-only) + a frozen version per publish; the trainee
  always reads the newest version. Meals with portions per group in 0.5 steps, vegetables free, options (food
  lines or free text), tips. Kcal and every publish rule are computed on the server; preference conflicts
  (diet / allergy / kosher) are warnings next to the line.
- Trainee: a Nutrition tab (Home · Workouts · Nutrition · Profile). Meals as portion chips; tapping a portion or
  a food line opens every swap of that group. No calorie number reaches her (the server never sends one).
- Onboarding: a "Nutrition preferences" step before Review (placeholder copy), saved per step, shown in Review,
  editable from Profile; the coach sees it in both apps ("Not answered" for earlier trainees).
- Tab dots (owner decision, instead of a trainee inbox): Workouts when a training plan was published or a
  published one changed, Nutrition when a new nutrition version was published — since she last opened that tab.
  "Last seen" is stored on the server, so it is the same on every device.

2. Defaults approved as starting points: fat loss −20%, recomp −10%, muscle gain +10%, maintenance 0; activity
   factors 1–2 days 1.375 · 3–4 days 1.55 · 5–6 days 1.725 · 7 days 1.9 (training days = the rounded middle of her
   min–max answer, so "3–4" → 4); floor 1,200; suggestion rounded to 10 kcal.
3. "A / B" lines: the first item is the line; the second is reached through the swap list.
4. vegetablesFree: true on breakfast, lunch, dinner; false on the snack.
5. Allergies: the 8 allergens that have a diet tag (dairy / lactose, eggs, gluten, peanuts, tree nuts, sesame,
   soy, fish) + free text.
6. No trainee inbox: tab dots instead (see §1). The nutrition notifications are stored for Phase 5b push.
7. Diet tags proposed for the coach to review — the full table is in
   docs/reference/nutrition-diet-tags-review.md (gitignored: it lists the guide's items, so it can't go into this
   committed report). It also notes the points worth checking (protein powder, vegetarian burger, oats, the
   rice / ptitim / couscous and buckwheat / barley lines tagged gluten as a whole, dark chocolate, and a possible
   typo in one item's name as written in the guide).

Schemas (as approved):
- FoodItem: coachId, group, name, portion, grams|null, kcal|null, isNew (stored as `isNewItem` — `isNew` is a
  reserved Mongoose path; the API field is still `isNew`), dietTags, order, archivedAt, seedKey (idempotent seed).
- OnboardingResponse.answers.nutritionPreferences: dietType, kosher, allergies[], allergyNotes, dislikes (≤500).
- NutritionSettings (per coach): overrides of the config; unset = default.
- NutritionPlan (unique traineeId): calorieTarget { kcal, source suggested|override, goal, formulaSex,
  suggestion (snapshot with inputs), floorConfirmation { kcal, floorKcal, confirmedAt } }, meals, tips,
  waterGoalMl (13b), templateId, publishedVersion, publishedAt.
- NutritionPlanVersion: a frozen copy per publish + the group values and kcal at that time (unique planId +
  version). The trainee view joins the live food items (so a fixed typo shows; archived items still resolve).
- Shared meal subschema (nutritionMeal.schema.ts): meals → options → lines { kind food|text|recipe, foodItemId,
  recipeId, group, portions, text }, every level with a stable _id (13b meal logs point at meal ids).
- Template: type 'nutrition_plan' + field `nutrition` { targetKcal, meals, tips } (same meal subschema). The
  pre-validate rule per type: nutrition templates have ≥1 meal and no workouts; other types have no `nutrition`.
- 13b (models only, no routes): Recipe, MealLog (unique traineeId + date + mealId, planned snapshot), WaterLog
  (unique traineeId + date). Quick-add amounts in nutrition.config.ts.

Feature flags (13b): apps/server/src/config/features.ts — env FEATURE_NUTRITION_RECIPES / FEATURE_MEAL_LOGGING /
FEATURE_WATER_TRACKING, 'true' opens one, default OFF (documented in .env.example, blanked in vitest.config).
`requireFeature(flag)` answers 404 for a closed feature (13b mounts its routes behind it). While closed, the plan
save refuses `recipe` lines and `waterGoalMl` (400) and the trainee API leaves the water goal out. Both nutrition
responses carry `features` so the apps hide UI by what the server says.

Floor: a target below the floor keeps / gets a confirmation only when the coach ticks "I confirm this target",
and only for that exact kcal — changing the target drops it. Publish re-checks against the floor of the coach's
config at publish time; the confirmation is copied into the version.

Things I decided inside your answers (say if you want any changed):
- Republishing with nothing changed is refused (409) — no empty "plan updated" notifications. A change of the
  calorie target alone counts as a change (it is part of the version) although the trainee doesn't see kcal.
- The working copy always autosaves (1.5 s after the last change): unlike training plans, the trainee only ever
  sees published versions, so there is no "published plan saves explicitly".
- A new plan starts with four placeholder meals (Breakfast / Lunch / Snack / Dinner, PRD default list), the goal
  mapped from her onboarding goals and no target; nothing is stored until the coach changes something.
- Starting from a template replaces meals + tips (fresh ids) after a confirm; the template's target is used only
  when her plan has no target yet (as an override).
- Settings refuse a group value lower than a food item's kcal (409, "lower them first") — the cap rule must keep
  holding.
- The seed is idempotent per coach: items and the template already seeded are left as they are (the coach may have
  edited them). seed:dev also runs it when the data file exists. The seed's dev trainees now include nutrition
  preferences (fresh databases only — existing seed trainees keep theirs).
- Workouts dot: Plan.liveUpdatedAt is set on publish and on every save of a published plan (older plans fall back
  to publishedAt). Opening any /workouts or /nutrition screen clears that tab's dot.
- Review step: it showed no answers before; it now shows the new step's answers only (placeholder heading). The
  Profile page got a "Nutrition preferences" block with the usual edit link.
- Preference conflicts are computed only on the server (warnings after the autosave), not marked in the food picker,
  so the rules stay in one place.
- The Phase 12 AI training draft never sees the nutrition preferences (its profile is an explicit allowlist).
