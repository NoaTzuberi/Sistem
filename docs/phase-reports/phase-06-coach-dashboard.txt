================================================================================
1. SUMMARY
================================================================================
- Dashboard: Trainees list (search, status filters, the prominent "Needs next week's plan"
  filter, 48h window, last activity), Trainee detail (Onboarding / Plans / Workout logs /
  Body metrics tabs), Plan builder, and a notifications bell in the top bar.
- Plan builder: workouts and exercises with drag and drop (@dnd-kit) plus ↑ ↓ buttons,
  exercise library search, simple targets (sets, reps or range, or seconds, kg, rest),
  per-set targets (warm-up / working / drop rows), supersets, notes, duplicate workout.
- Draft plans autosave 2.5 s after the last change ("Saving… / Saved"); published plans
  keep an explicit "Save changes" button because edits go live.
- Server: create / duplicate last week / save / publish / unpublish / delete under
  /api/coach, coach-only and scoped to the coach's own trainees. Publishing emits
  'plan.published' once (the Phase 5a listener notifies the trainee).
- A plan the trainee has started (any workout log) is locked: editable, but it cannot be
  unpublished or deleted.

================================================================================
2. DECISIONS (owner answers) AND HOW THEY WERE BUILT
================================================================================
1. Statuses — new: onboarding not finished · waiting: finished, no published plan ·
   active: a published plan for this week or later · inactive: only older published plans.
   "Needs next week's plan" = active AND no plan at all (draft or published) for next week.
   Computed on the server in the trainee's time zone (coach.service resolveTraineeStatus).
2. Exercise search = every imported exercise that is active and not rejected, through the
   new coach-only GET /api/coach/exercises. Facts only (name, muscle, equipment, level,
   type). The public /api/exercises is unchanged.
3. Edits to a published plan are live, with no notification. Unpublish / delete are allowed
   only while the trainee has no workout log for the plan (409 afterwards). After an
   unpublish the trainee's app state is 'waiting' again if she has no other published plan
   (it is computed from her published plans on /auth/me and the waiting poll).
4. A newly added exercise starts at 3 sets × 10 reps, no weight, no rest.
5. Autosave for drafts only; explicit save for published plans.
6. @dnd-kit added for reordering; ↑ ↓ buttons kept; handles also work from the keyboard
   (Space to pick up, arrows, Space to drop).

Things I decided inside those answers (say if you want any changed):
- Plan rules live only on the server. A refused save / publish returns `issues` with the
  workout and exercise position, and the builder shows each one next to its row.
- Publish needs: at least one workout, every workout with at least one exercise, and every
  superset label used by 2+ exercises that are next to each other. A published plan must
  keep meeting these rules when it is edited. Drafts only need valid rows.
- A new workout gets the placeholder title "Workout N" (a workout cannot be saved without
  a title).
- New plans can only be created for this week or later; the dashboard offers this week and
  the next three.
- "Duplicate last week" copies the most recent EARLIER plan (draft or published) into the
  chosen week as a draft, with new workout / exercise ids.
- Publishing the same plan again after an unpublish does not notify the trainee a second
  time (Phase 5a rule: one notification per plan).
- Exercise names in plans: the coach endpoints add the exercise facts to each plan
  exercise. The trainee endpoints (/api/plans) do not yet — Phase 7 / 8 need the same.

3. API (all need role=coach; :traineeId must be the coach's own trainee, else 404)
================================================================================
  GET    /api/coach/exercises?search&muscle&equipment&difficulty&page&limit
  GET    /api/coach/trainees                      -> { items, serverTime }
         items now carry status, planDueAt, needsNextWeekPlan, lastActivityAt,
         currentWeekStart
  GET    /api/coach/trainees/:traineeId           -> { trainee, serverTime }
  GET    /api/coach/trainees/:traineeId/plans     -> plans with `locked` + exercise facts
  POST   /api/coach/trainees/:traineeId/plans     { weekStartDate, duplicatePrevious? }
         201 · 400 not a Sunday · 409 past week / week taken / nothing to duplicate
  GET    /api/coach/trainees/:traineeId/plans/:planId
  PUT    /api/coach/trainees/:traineeId/plans/:planId   { notes?, workouts[] } (whole plan)
         400 { message, issues[] } · existing workout / exercise ids are kept
  POST   /api/coach/trainees/:traineeId/plans/:planId/publish     400 { issues } if not ready
  POST   /api/coach/trainees/:traineeId/plans/:planId/unpublish   409 if locked
  DELETE /api/coach/trainees/:traineeId/plans/:planId             204 · 409 if locked

  workout, back to simple). A designed dialog is a design decision for later.

  exception to "no inline styles"; there is no other way to follow the pointer.
- Wording everywhere is a functional placeholder (labels, messages, "Workout N").
  Onboarding answers are shown as humanized ids ("Build muscle"), not the app's wording.
- Exercises can only be reordered inside their workout, not dragged to another workout.
- Workout logs show a text slot instead of the Daily Pump photo, and body metrics show
  photo poses only — signed photo URLs arrive in Phases 9 / 10.
- An in-app link away from a PUBLISHED plan with unsaved changes drops them without a
  question (closing / reloading the tab does ask). Drafts are saved on leaving.
- If two browser tabs edit the same plan, the last save wins.
- The coach library search scores all ~2,900 exercises in memory per request. Fine at this
  size; the stale "~100 published" comment in exerciseSearch.ts was left as it is.
