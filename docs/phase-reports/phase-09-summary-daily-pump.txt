PR rules (apps/server/src/features/personalRecords/personalRecordDetection.ts — pure):
- weight   — heaviest weight on a rep set (≥1 rep) above every earlier working rep set
             of that exercise. A weighted hold is not a lift.
- reps     — more reps than ever at a weight she has lifted before (no weight = 0 kg =
             bodyweight). A weight she has never done is a baseline. The heaviest such
             weight wins.
- duration — a longer hold (timed set, no reps) at the same weight (or none). Interval
             sets of THIS workout never count (they run on the coach's clock). Her earlier
             interval sets do count as history (finding them would need every old plan).
- One PR per exercise, priority weight → reps → duration, in workout order.
- Only sets marked done count. Discarded workouts and other trainees never count.
- Written once, after the conditional "in progress → completed" update, so a retried
  finish can't record twice (also a unique index on logId + exerciseId).
- stats.prCount = the number of PRs (was always 0).

The existing personalRecords feature (kept from ATLAS) — decision: KEEP, as the PR record.
- Since Phase 8 nothing wrote it, but /api/personal-records, the Profile stats
  (/api/dashboard recentPersonalRecords) and AchievementBadges still read it, and Phase
  11's "new personal record" achievement needs stored PR events. Phase 9's finish is now
  its only writer.
- Schema: + logId (required, ref WorkoutLog), + weight (optional), type + 'duration'.
  Fresh database, so no migration. /api/personal-records items now also carry logId and
  weight. The mobile Profile type got 'duration'.

Photo flow:
- Phone (apps/mobile/src/features/workouts/data/photoCompression.ts): "Take photo"
  (file input with `capture`) or "Gallery" (without). Input ≤15 MB. Decoded with an
  <img> (browsers apply the EXIF rotation), drawn on a canvas at ≤1600 px on the long
  side, saved as JPEG 0.82 — redrawing drops all metadata, GPS included. No dependency.
  Uploaded at once, separately from rating/notes; progress %, Retry, Remove (confirm).
- Server: PUT /api/workout-logs/:id/pump-photo, raw body image/jpeg|png|webp (≤3 MB,
  privatePhotos/privatePhoto.middleware.ts answers 413/415 as JSON). Checks: her own log,
  status completed (409 otherwise), the file's first bytes are JPEG/PNG/WebP (400).
  Uploaded as type `authenticated`, public id sistem/pump-photos/<traineeId>/<logId>-<random>,
  stored as JPG, limited to 2000 px (Cloudinary re-encodes, a second metadata strip).
  Only the public id is stored. Replacing deletes the old asset (the log update returns
  the replaced photo, so concurrent uploads delete the right one); DELETE …/pump-photo
  removes it. A failed delete on Cloudinary is logged, not shown to her.
- Viewing: every read endpoint (her log, her list, the finish response, the coach's
  list) returns pumpPhoto { uploadedAt, url, urlExpiresAt }. url =
  cloudinary.utils.private_download_url(…, type 'authenticated', expires_at now + 1 h),
  signed locally after the access check. The link carries the asset path and the
  (non-secret) API key, never the secret. Cloudinary's CDN signed URLs would never
  expire; expiring CDN tokens are a paid add-on — switching later changes only
  photoUrl() in privatePhotos/privatePhoto.service.ts. Trade-off: no CDN caching, no
  resizing (a ~300 KB photo is loaded whole; the lists load it lazily).
- Expired link on an open screen: the image fails once → the screen refetches the log
  (new link). Each link is retried once.
- Who can see it: the trainee (her own logs only — another trainee gets 404) and her
  coach (loadCoachTrainee — another coach gets 404, a trainee on coach routes 403).

Summary API: PATCH /api/workout-logs/:id/summary { rating?: 1–5 | null, notes?: string
| null } — completed logs only (409), notes trimmed, ≤1000 chars, empty = cleared.
