2. DECISIONS (owner answers) AND HOW THEY WERE BUILT
================================================================================
1. Past plans stay on the dashboard. The app shows this week + next week only.
2. Status file shared, not copied -> new packages/shared (@sistem/shared).
   Why a new package and not an existing one:
   - @sistem/types is types only (the server imports it with `import type`); runtime
     code there would break that rule.
   - @sistem/api-client is the HTTP layer (axios); labels and sorting are not API calls.
   - @sistem/tokens is CSS.
   What is in it (all moved out of apps/dashboard, nothing rewritten):
   - traineeStatus.ts   status labels, tones, filters, urgency sort (+ matchesSearch)
   - format.ts          date / time-left / duration helpers (+ formatWeekRange, new)
   - onboardingSections.ts   the onboarding answers as sections of label / value rows
   - coachNotifications.ts   describeCoachNotification: text + trainee for the bell and
                             the Inbox
   - hooks/useLoad.ts, hooks/useServerNow.ts
   You asked for the status file. I moved the other five too, because the app needed
   each of them and the only alternative was a second copy — the thing you ruled out.
   Say if you want any of them back inside the dashboard.
   Like the other packages it has no build step; it has React as a peer dependency
   (for the two hooks). The server must never import it.
3. "Workout completed" -> one bullet added to Phase 8 in docs/BUILD_PLAN.md.

Things I decided inside those answers (say if you want any changed):
- "Duplicate last week and publish" targets this week if it has no plan, otherwise next
  week, and is offered only when an earlier plan exists. It runs the two existing calls
  (create with duplicatePrevious, then publish). If the publish is refused, the copy
  stays as a draft and the screen says so, with the server's reasons.
- A refused publish lists the server's `issues` ("Workout 2, exercise 1: ...") and says
  to fix it on the dashboard. The app checks no plan rule itself.
- The tone type in the shared file is 'neutral' | 'accent' | 'solid'. The mobile Badge
  got a 'solid' variant (white on Cherry Rose) so both apps draw the same three tones.
- The trainee section is kept in the URL (?tab=plan), so reload and back keep it.
- The unread count is one small store (features/notifications/unreadCount.ts): polled
  every 60 s and on window focus, and updated by the Inbox when something is read.
- Notification types the coach view does not know are skipped, so the Phase 8 type can
  be added in one place.

2b. FIX AFTER REVIEW — DASHBOARD NOTIFICATIONS PANEL OFF-SCREEN
================================================================================
Reported: the bell's dropdown panel opened off the side of the screen, partly cut off.
Cause: the panel is 360px wide and hangs leftwards from the bell's right edge. The bell
is not at the window's right edge (the name and "Log out" sit after it), so in a narrow
window its right edge is less than 360px from the left and the panel ran off the LEFT
side. Measured before the fix: at 375px wide the panel started at -69px. At 768, 1024
and 1440 it was already inside, so I could only reproduce the bug below about 470px;
if you saw it in a wider window, tell me the width.
Fix (CSS only):
- Width is min(360px, 100vw - 32px); a long list scrolls inside the panel (max height
  is the smaller of 70% of the window and the window minus the bar).
- At 768px and below the panel is placed against the top bar instead of the bell: full
  width with a 16px margin on each side.
- The coach's name in the top bar is cut at 200px, so a long name cannot push the bell
  (and the panel) to the left.
Measured after the fix (panel left–right edge / window width), bell opened, then with
40 extra rows to force a long list: 1440: 885–1245 · 1024: 469–829 · 768: 16–752 ·
480: 16–464 · 375: 16–359. Always inside, list scrolls inside the panel, page width
never grows.
Mobile app: nothing opens a dropdown panel. The Inbox is a full screen, and the confirm
sheet is a full-width bottom sheet (0–373 of 373 at the 375 frame, measured during the
Phase 6b check — not measured again for this fix, no mobile file changed).
