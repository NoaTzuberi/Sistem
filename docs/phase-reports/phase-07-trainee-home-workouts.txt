2. DECISIONS (owner answers) AND HOW THEY WERE BUILT
================================================================================
Status rule (server only: apps/server/src/features/plans/planStatus.ts)
  today      = the calendar date of the server's clock in User.timezone (planWeek.ts)
  this week  = the plan whose weekStartDate is the Sunday of today's week
  date       = weekStartDate + dayOfWeek (null when the coach set no day)
  done       = a WorkoutLog with status 'completed' for that plan + workout (wins, even late)
  missed     = not done and date < today; a workout with no day: only once today is past
               its week's Saturday
  upcoming   = everything else (+ flags isToday and inProgress)
  next       = in progress → first upcoming (plan order) → earliest missed → none
1. A missed workout stays tappable until the end of its week; "Start next workout" falls
   back to the earliest missed one. Past weeks: missed rows are plain text, not links.
   "Missed" is a placeholder label in features/workouts/data/workoutCopy.ts.
2. "Start next workout" opens the read-only workout detail (exercises, sets, superset bar,
   coach notes, and a "coming soon" line where the Phase 8 start button goes).
3. Deleted WorkoutsPage (ATLAS), the builder, the template detail, their routes and
   components. ActiveWorkoutPage and WorkoutSummaryPage stay, unrouted. CLAUDE.md updated.

Server workoutTemplates — what I checked and what I removed:
  - Nothing outside the feature used its routes, controller, service, validation or the
    seed script → DELETED, with `/api/workout-templates` and the `seed:workout-templates`
    npm scripts (root + server) and its README line. The mobile workoutTemplatesService
    (the only caller) was deleted with the ATLAS screens.
  - The MODEL, constants and types are still imported by the ATLAS workouts feature
    (apps/server/src/features/workouts/workout.service.ts: startWorkout reads a
    WorkoutTemplate; the Workout model refs it) → KEPT until Phase 8 replaces ATLAS
    Workout. Note: with the routes gone, no template can be created any more, so the
    ATLAS /api/workouts start call is dead in practice — nothing routed calls it.
  - The Phase 3 `templates` model is untouched.

Things I decided inside your answers (say if you want any changed):
- API shape: GET /api/plans/week (Home), GET /api/plans now { items, today,
  nextWeekStartDate, serverTime }
  with a `period` (past / current / upcoming) on each plan, GET /api/plans/:id with the
  same statuses. All published-only and scoped to the caller, as before.
- "Next week" section (added after review, your request): shown above past weeks only
  when a PUBLISHED plan exists for next week. Read-only; tapping a workout opens its
  detail (status "Upcoming"). The server sends nextWeekStartDate, so the app picks the
  plan by comparing dates it was given — no date math on the device. Plans the coach
  published two or more weeks ahead stay hidden until they become next week; drafts
  are never visible.
- Old DashboardPage widgets: ProfilePage still uses StreakRing, WeekDotStrip, MilestoneBar
  and AchievementBadges (plus /api/dashboard), so those stay until Phase 10 / 11. Home
  reuses StreakRing (shown empty at 0 with "Coming soon"). WeekDotStrip counts "last
  7 days", which doesn't fit a plan week, so Home has a new WeekStrip built on the same
  idea. Deleted: DashboardPage, DashboardCalendar, MonthCalendar.
- Week strip marks (placeholder look): filled Cherry Rose = done, ring = upcoming, grey
  ring with a slash = missed, small grey dot = no workout; today is outlined pink.
- Shared, not copied: describeTargets / DAY_NAMES and the log-set helpers moved from
  coach mode into @sistem/shared; the exercise list of a planned workout is one
  component (PlanExerciseList) used by coach mode and the trainee; CoachMessage became
  components/common/StateMessage (same look) for the loading / empty / error lines.
- Back button on the detail screens goes back in history; opened directly (reload, deep
  link) it goes to Workouts.

2c. DASHBOARD FIX — NEW PLANS SILENTLY LANDED ON A LATER WEEK ("OCT 25")
================================================================================
What you saw: a new plan / its workouts were for the week of Oct 25, not this week.

Investigation (before changing anything):
- weekStartDate itself was right everywhere. The server computes the current week from
  its own clock in the trainee's stored time zone (planWeek.currentWeekStart). On
  Mon 5 Oct, 15:25 Jerusalem it gave Sun 4 Oct for every trainee in your dev DB
  (checked through GET /api/coach/trainees: serverTime 12:25Z, currentWeekStart
  2026-10-04, Asia/Jerusalem). Sunday logic and dates are tested and were fine.
- The week was chosen in the dashboard (TraineePlans.tsx), not on the server: it
  offered this week + the 3 after it and, unless you picked one, used THE FIRST WEEK
  WITHOUT A PLAN. "New plan" and "Duplicate last week" both used that week.
- Your dev DB: Dev Trainee One (trainee1) had Sep 27 (published), Oct 4 (draft, 0
  workouts), Oct 11 (draft), Oct 18 (published) — so the first free week was Oct 25,
  chosen without telling you. The Oct 25 plan in your DB was created today at 12:17
  UTC (15:17 your time) for Dev Trainee One. Dev Trainee Two (trainee2) really has only
  the Sep 27 plan; for them the old code would have picked Oct 4 correctly. So the
  trainee where it happened had 4 plans, not 1 — the Oct 4 and Oct 11 drafts are easy
  to miss (Oct 4 has no workouts). If you saw it on another trainee, tell me which.
- Root cause: the client-side "first free week" fallback. It skipped weeks that
  already had a plan instead of showing them, and nothing on screen said which week
  was used. The builder header ("Week of Sun, 25 Oct 2026") was the only clue.

Fix + feature (as you asked):
- The server now decides the weeks and the defaults: new GET
  /api/coach/trainees/:traineeId/plan-weeks (coach only, own trainee — else 404) ->
  this week, next week and the 6 after them, each with its plan (id + Draft /
  Published) or none, and the week a duplicate would copy from. Past weeks are never
  offered (and the create endpoint still refuses them, 409).
  Defaults: "New plan" -> this week, always. "Duplicate last week" -> this week, or
  next week when this week already has a plan.
- Dashboard: "New plan" and "Duplicate last week" open a week picker. "This week ·
  Oct 4–10" and "Next week · Oct 11–17" are first; "Later…" shows the other 6. A week
  with a plan shows Draft / Published and "Open", and choosing it turns the button
  into "Open plan" — it never moves to another week. For a duplicate it says which
  week is copied ("Copies the plan of Sep 27 – Oct 3").
- Plan builder header: "This week · Sun, Oct 4 – Sat, Oct 10" ("Next week · …" or just
  the dates for other weeks). The plans list uses the same short dates + This / Next
  week badges.
- Test that reproduces it: apps/server/src/features/plans/__tests__/planWeekOptions.test.ts
  rebuilds Dev Trainee One's plans at Mon 5 Oct 15:25 Jerusalem and checks the defaults
  are Oct 4 / Oct 11 and nothing points at Oct 25; also trainee2's case, no past weeks,
  time zone at Saturday midnight, 404 / 403. (The old picker was client code with no
  client tests, so the test pins the server's choice the picker now follows.)
- Not changed: mobile coach mode ("Duplicate last week and publish" already targets
  this week, else next week, and the server refuses a taken week).

Checked in the browser against your dev DB (dashboard, signed in as the dev coach):
- Dev Trainee One: New plan -> "(*) This week · Oct 4–10 Draft Open", "Next week ·
  Oct 11–17 Draft Open", footer "…already has a draft plan · Open plan". Later… ->
  Oct 18 Published, Oct 25 Published, Nov 1 – Nov 22 free. Duplicate last week ->
  preselects Next week (Oct 11, Draft -> Open plan). Open -> builder header "This week ·

- Dev Trainee Two: New plan -> This week Oct 4–10 preselected, "Create plan ·
  Oct 4–10". Duplicate -> Oct 4–10, "Copies the plan of Sep 27 – Oct 3".
- I did NOT click Create / Duplicate (it would add real plans to your dev DB).
- The console showed errors from while I was editing (Vite hot reload picked up one
  file before the other was saved; that also logged the dashboard out once). After a
  full reload there were no errors.
- Wording in the picker is placeholder.
