================================================================================
1. SUMMARY
================================================================================
- One config file (achievement.definitions.ts) holds the 28 achievements, one line each.
  Each line names a metric and a threshold (one-time) or `repeatable`. Metrics are pure
  timelines over her history, so the same code awards live and backdates the backfill.
- Evaluation runs on the server after a workout finish (after the PRs), a Daily Pump upload,
  a body save and a progress photo upload. It is idempotent (unique traineeId + key), never
  takes an achievement back, never fails the save, and each run catches up on anything missed.
- Streak = consecutive weeks that reach the completion ratio (config, default 1.0). Weeks
  without a plan are neutral. The week in progress never breaks the streak.
- The phone shows unlocks in three places:
  - the summary: they pop in (GSAP), then are marked seen
  - a celebration sheet: after a body save, and on Home for anything not celebrated yet
  - Home's "Recent achievements" strip and its streak ring
  Profile has "Your progress" and a full Achievements screen.
- The coach sees the trainee's streak, numbers and every achievement (date or progress) in a
  new Achievements tab, in the app and in the dashboard.
- Backfill: `npm run backfill:achievements` was run on the dev database. It gave trainee 2 seven
  achievements. A second run added none.

2. DECISIONS (owner answers) AND HOW THEY WERE BUILT
================================================================================
Owner decisions:
1. PR achievements are milestones only (first weight PR, first reps PR, 10 / 25 / 50 PRs). There
   is no achievement per PR.
2. Weeks with no published plan (or a plan with no workouts) are neutral: skipped, they neither
   add to nor break the streak.
3. Achievement.seenAt + the celebration sheet were added.
4. /api/personal-records is deleted (404 now, tested).
A. ACHIEVEMENT_CONFIG.streakWeekCompletionRatio (default 1) sets when a week counts toward the
   streak: done / planned ≥ ratio. Workouts needed = ceil(ratio × planned), never fewer than 1,
   with a small epsilon so 0.7 × 10 needs 7. perfect_week always needs 100%. Unit-tested at
   1.0 and 0.75 (3 of 4 counts at 0.75, breaks at 1.0; 3 of 3 is needed at 0.75; a 3-of-4
   week is never a perfect week).
B. comeback: repeatable, key comeback:<logId>. A completed workout at least 14 calendar days (in
   her time zone) after her previous completed workout. Example: 1 Oct → 15 Oct counts, 1 Oct →
   14 Oct does not. Her first ever workout is never a comeback. The 14 is
   ACHIEVEMENT_CONFIG.comebackGapDays.
- PRD §7 now says: "No achievements are based on body weight gain or loss — trainees have
  different goals and weight-based rewards can be harmful." weigh_ins_10 counts days with a
  weight logged and never reads the values (a test checks this).
- Phase 14 — Cardio & running is in docs/BUILD_PLAN.md after Phase 13. A follow-up owner
  decision rewrote it around smartwatch integration (manual logging as the fallback):
  14a cardio foundation (web: targets, intervals, HR zones, manual logging, import-ready data
  model, cardio PRs and achievements), 14b watch import via HealthKit / Health Connect (after
  Phase 5b), 14c direct Strava / Garmin integrations (optional, API terms to verify first).
  How the engine leaves room for it:
  - achievementMetrics.ts takes new facts in AchievementHistory and new metrics in the METRICS
    registry; the evaluator doesn't change.
  - PERSONAL_RECORD_TYPE_IDS takes new types, and the PR metrics are built per type by a factory.

The achievement list (names are PLACEHOLDERS, in @sistem/shared achievementDisplay.ts):
  One-time:
    first_workout, workouts_5/10/25/50/100                      completed workouts
    first_weight_pr, first_reps_pr                              PersonalRecord of that type
    prs_10/25/50                                                PersonalRecords of any type
    volume_10k/50k/100k/500k/1m                                 lifetime total volume (kg)
    streak_2/4/8/12/26/52                                       longest streak (weeks) reached
    first_pump_photo                                            Daily Pump photo
    first_measurement, first_progress_photo, weigh_ins_10       body tracking
  Repeatable:
    perfect_week (perfect_week:<weekStartDate>), comeback (comeback:<logId>)

Streak rules (achievements/streak.ts, pure, unit-tested):
  - Week = the plan's weekStartDate (Sunday, her zone); "today" is in her stored zone.
  - A week counts when done / planned ≥ ratio. done = planned workouts with a completed log
    (abandoned / in-progress logs never count; a log finished late still counts, the same rule
    as the Home status).
  - A week breaks the streak when it has ended without reaching the ratio.
  - Weeks without a plan, or with an empty plan, are skipped. Future weeks are ignored.
  - current = the run up to now; best = the longest run ever. thisWeek = { done, planned } for
    the ring.
  - The streak is computed on each read, never stored, so a coach's plan edit shows at once.
    Achievements already awarded stay.

Things I decided inside your answers (say if you want any changed):
- unlockedAt:
  - Live: the moment of the save.
  - Backfill: when the rule was met (the Nth workout's finish, the log that crossed a volume
    line or completed a week, the photo's upload).
  - Body days have no per-field time, so a body achievement's backfill date is when that day
    was first saved (its createdAt). Trainee 2's body achievements therefore show 6 Oct, the
    day her seed entries were created.
- Each unlock's source is the log or body day that met the rule:
  - The summary shows the achievements whose source is that log, including first_pump_photo
    right after the upload.
  - Streak / perfect-week unlocks point to the workout that completed the week.
- Repeatable achievements in progress lists show "×N". Locked one-time achievements show
  "current / target" with a flat native <progress> bar (no inline styles).
- Celebration:
  - One queue for the whole app (features/achievements/celebration.ts) and one sheet, mounted
    once in AppRouter, for trainees only.
  - Closing it ("Nice!", ✕, Esc or the backdrop) marks everything shown as seen.
  - Home queues every unseen achievement on load. The summary marks its own as seen once they
    have popped in, so they aren't celebrated again on Home.
  - With reduced motion nothing pops; the items simply show.
- The coach's views never mark anything seen.
- No notification is stored for an unlock (PRD §9 "in-app" = the summary reveal + the
  celebration). Phase 5b can add push through an `achievement.unlocked` event.
- Icons: features/achievements/data/achievementIcons.ts maps a type to your image. Without one,
  a placeholder badge shows: a pink cut tile with a trophy, or grey with a lock when locked.
- Profile's old "Your Progress" card (day-based streak, MilestoneBar, WeekDotStrip, the
  client-computed AchievementBadges) is replaced by:
  - the streak (current, best, this week)
  - Workouts / Total volume / PRs / Achievements N of 28
  - an "Achievements" link above Settings
- Home: the streak ring sits where the placeholder was (weeks in the middle, this week's done /
  planned on the ring). The strip shows the latest 6 and a "See all" link.
- The coach tab in the app is "Achievements". The five tabs now share the width (flex) and
  scroll sideways only if a label can't fit; at 375 px they fit.
- /api/achievements is trainee-only now (requireRole('trainee')). The coach reads through
  /api/coach/trainees/:id/achievements (loadCoachTrainee).
- The api-client's saveBodyMetric / uploadProgressPhoto now return { metric,
  achievementsUnlocked } instead of the metric alone. The three callers were updated.
