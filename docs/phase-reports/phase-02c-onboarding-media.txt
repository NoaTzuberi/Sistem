================================================================================
1. SUMMARY
================================================================================
- The 30 onboarding clips (1,066.9 MB) were compressed with ffmpeg to 63.0 MB (-94.1%) +
  2.7 MB of posters, and uploaded to Cloudinary (sistem/onboarding/videos|posters/<activityId>).
- Two re-runnable server scripts: `media:compress` (ffmpeg, before/after report) and
  `media:upload` (Cloudinary SDK, skips unchanged files by MD5, writes the manifest).
- Onboarding reads the clips from onboardingMedia.json (URLs only). The poster shows first;
  the video is fetched only when an activity is previewed and fades in once it really
  plays. On error, a slow network (8 s visible without playing) or Data Saver / 2G, the
  poster stays.
- No video is imported into the client bundle anymore: the mobile build output went from
  ~1 GB of .mp4 to 0 (dist is 1.4 MB). The originals are untouched and still gitignored.
- Build, lint and tests pass; `npm run dev` works; onboarding was checked in Chrome playing
  the clips from Cloudinary.

================================================================================
2. DECISIONS (approved in chat)
================================================================================
- ffmpeg settings: short side <= 720 (never upscaled), H.264 High, yuv420p, CRF 26,
  -maxrate 2M -bufsize 4M, fps capped at 30 (only clips above 30), first video stream only,
  no audio/subtitle/data tracks, no metadata, +faststart, -preset slow. Owner checked the
  Skiing clip (204.1 MB -> 4.1 MB) and kept the 2 Mbps cap.
- Poster = first frame of the compressed clip (JPG, q 3), so it matches playback start.
- Cloudinary public ids by activity id (not the original file names). Public delivery: this
  is stock footage, not personal data. Daily Pump / progress photos (Phases 9–10) will use
  authenticated delivery + signed URLs.
- Official `cloudinary` SDK in apps/server (also needed later for signed photo URLs).
- Manifest is committed at apps/mobile/src/features/onboarding/data/onboardingMedia.json:
  per activity { video, poster, videoMd5, posterMd5 }. No credentials. The URLs carry the
  Cloudinary version (v…), so an overwritten file is never served stale.

Scripts (from the repo root; need apps/server/.env with the CLOUDINARY_* keys):
- npm run media:compress -w @sistem/server                    all clips, skips existing output
- npm run media:compress -w @sistem/server -- --only skiing   one or more ids (comma-separated)
- npm run media:compress -w @sistem/server -- --force         re-encode even if output exists
  Reads apps/mobile/src/assets/onBoardingvid/ (never modified), writes
  apps/server/data/onboarding-media/{videos,posters}/, prints before/after per file + total.
- npm run media:upload -w @sistem/server                      uploads changed files only
- npm run media:upload -w @sistem/server -- --only skiing / --force
  Writes apps/mobile/src/features/onboarding/data/onboardingMedia.json (commit it).
  Never prints credentials (Cloudinary error messages are redacted).
- Adding/replacing a clip: put the original in onBoardingvid/, map it in
  ONBOARDING_VIDEO_SOURCES (onboardingMedia.constants.ts), then
  media:compress -- --only <id> --force and media:upload -- --only <id>.

Manual checks for you:
1. `npm run dev`, register a new user, go to step 5 (Activities), tap a few activities:
   poster appears at once, the clip fades in and loops. DevTools -> Network -> "mp4": only
   res.cloudinary.com requests, none from localhost.
2. DevTools -> Network -> Offline, tap another activity: poster (if cached) or the dark
   background, no broken video icon; the step stays usable.
3. Build: `npm run build -w @sistem/mobile` then `ls apps/mobile/dist/assets` — no .mp4.
4. After you move apps/mobile/src/assets/onBoardingvid/ out of the repo: build + onboarding

5. Real phone (`npm run dev -w @sistem/mobile -- --host`), mobile data: clips start within a
