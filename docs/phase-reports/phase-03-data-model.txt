Scope: docs/BUILD_PLAN.md Phase 3 (items 1–5). Schemas were shown first and approved in chat

Built on Phase 2's role / appState / requireRole — not redone.

================================================================================
1. SUMMARY
================================================================================
- User model: onboardingStatus (replaces the stored boolean), onboardingCompletedAt (server
  time), coachId, pushTokens (never sent to clients), timezone (default Asia/Jerusalem, device
  zone sent on sign-up). Sign-up assigns the default coach (never fails without one).
- New models: OnboardingResponse, Plan (embedded workouts -> exercises), WorkoutLog,
  BodyMetric, Achievement, Template. Units everywhere: kg, cm, seconds.
- Onboarding moved from User.profile to OnboardingResponse: GET/PATCH /api/onboarding
  (one step at a time) + POST /api/onboarding/complete. PUT /api/users/profile is gone;
  GET /api/users/profile keeps its old shape so the Profile page is unchanged.
- One set resolver (plans/planSets.ts) turns a PlanExercise into concrete sets; the API
  returns it as `resolvedSets`, so no screen re-implements it.
- Ownership: trainee routes filter by the caller; coach routes (/api/coach/...) use
  requireRole('coach') + loadCoachTrainee (trainee.coachId === coach). seed:dev script.
- Build, lint and tests pass (138 tests, was 56); `npm run dev` works; the real onboarding
  flow was clicked through in Chrome.

================================================================================
2. DECISIONS (approved in chat)
================================================================================
A. Coach on sign-up: DEFAULT_COACH_EMAIL -> else the only coach -> else coachId null.
   promote:coach and seed:dev assign unassigned trainees when the coach is the default one.
B. Targets: reps + optional repsMax (a range), plain numbers.
C. One plan per trainee per week (unique index); a draft becomes published in place.
D. Weights stored in kg, body measurements in cm (stated in the schemas); apps convert.
E. ATLAS Workout / Progress / WorkoutTemplate stay side by side until Phases 8 / 10 / 6.
Additions:
1. Time-based exercises: PlanExercise.durationSec; every exercise (and every set target) needs
   reps OR durationSec. WorkoutLog sets have durationSec.
2. Supersets: PlanExercise.supersetGroup (1–3 chars, A–Z/0–9, stored uppercase).
3. Per-set targets: PlanExercise.setTargets [{ type warmup|working|drop (default working),
   reps?, repsMax?, durationSec?, targetWeight?, restSec? }]. When present it defines every
   set: `sets` is derived from its length (set on validate), each entry needs reps or
   durationSec, and there is NO fallback to the uniform fields (e.g. restSec must be set per
   entry). Without it the uniform fields apply to each of `sets` working sets.
   WorkoutLog sets carry `type` copied from the target.
Also added to PRD §14 Backlog: coach custom exercises with her own demo video (Cloudinary).

Implementation choices worth knowing:
- Plan.weekStartDate and BodyMetric.date are 'YYYY-MM-DD' strings (date-only, no UTC
  day-shift). weekStartDate must be a Sunday; weeks are computed in the trainee's zone
  with Node's built-in Intl (plans/planWeek.ts) — no date library added.
- `resolvedSets` is computed on the server in every plan response (trainee and coach).
  The helper can't live in a shared package because @sistem/types is types-only and the
  server can't import TS source at runtime; serving the resolved list is what keeps the
  logic in one place.
- Photos (WorkoutLog.pumpPhoto, BodyMetric.photos) store a Cloudinary public id, not a URL
  (PRD §10 says pumpPhotoUrl): private photos get a fresh signed URL on read (Phases 9/10).
  The id is never sent to clients.
- Template stores typed `workouts` (the Plan workout subschema) instead of PRD's untyped
  `content`; type 'workout' holds exactly 1 workout, 'plan' at least 1.
- AuthUser keeps `onboardingCompleted` (computed from onboardingStatus) so existing screens
  work, and gains onboardingStatus, onboardingCompletedAt (for the Phase 4 timer), timezone.
- An unknown device time zone on sign-up falls back to Asia/Jerusalem (sign-up never fails
  for it); a non-string value is a 400.
- Onboarding routes are trainee-only (requireRole('trainee')). Completing twice, or editing a
  step afterwards, never moves onboardingCompletedAt (the 48h start).
- Resource ownership is enforced inside the query (e.g. findOne({ _id, traineeId })), and a
  resource that isn't yours is 404, same as a missing one, so ids can't be probed.

3. SCHEMAS (as built)
================================================================================
User (changed)        + onboardingStatus not_started|in_progress|completed, onboardingCompletedAt,
                        coachId (ref User, null for coaches), pushTokens [{token, platform
                        ios|android, updatedAt}] select:false, timezone (IANA-validated).
                        - profile, - onboardingCompleted (stored). Indexes: {coachId, role,
                        createdAt:-1}, {'pushTokens.token'} sparse.
OnboardingResponse    userId (unique), answers (ATLAS profile shape, all optional until
                        completion), lastStep (step id), completedAt.
Plan                  traineeId, coachId, weekStartDate (Sunday, 'YYYY-MM-DD'), status
                        draft|published, publishedAt, notes, workouts[{_id, title, dayOfWeek
                        0–6, order, notes, exercises[{_id, exerciseId, sets, reps?, repsMax?,
                        durationSec?, targetWeight?, restSec?, notes?, supersetGroup?,
                        setTargets?}]}]. Indexes: {traineeId, weekStartDate} unique,
                        {traineeId, status, weekStartDate:-1}, {coachId, status, weekStartDate:-1}.
WorkoutLog            traineeId, planId, workoutId (PlanWorkout _id), workoutTitle (copy),
                        status in_progress|completed|abandoned, startedAt, finishedAt,
                        sets[{exerciseId, planExerciseId?, setIndex, type?, reps?, weight? kg,
                        durationSec?, completed, completedAt?}], stats?{durationSec,
                        totalVolume, setsCompleted, prCount}, rating 1–5, notes,
                        pumpPhoto?{publicId, uploadedAt}. Indexes: {traineeId, startedAt:-1},
                        {traineeId, planId, workoutId}, one in_progress log per trainee
                        (partial unique).
BodyMetric            traineeId, date 'YYYY-MM-DD', weight? kg, measurements? Map cm (keys
                        from BODY_MEASUREMENT_IDS: chest, waist, hips, arms, thighs), photos
                        [{publicId, pose front|side|back, uploadedAt}], notes. Index
                        {traineeId, date:-1}.
Achievement           traineeId, type, key, value?, unlockedAt, sourceLogId?,
                        sourceBodyMetricId?. Indexes: {traineeId, key} unique (never twice),
                        {traineeId, unlockedAt:-1}.
Template              coachId, type workout|plan, name, description?, workouts (Plan
                        subschema). Index {coachId, type, updatedAt:-1}. No routes yet (Phase 6).

4. API (new / changed)
================================================================================
Trainee (requireAuth; always the caller's own data):
  GET    /api/onboarding                  own answers, lastStep, status, name, units
  PATCH  /api/onboarding                  { step, answers } — only that step's fields
  POST   /api/onboarding/complete         every answer (same validation + messages as ATLAS)
  GET    /api/users/profile               unchanged shape, now read from OnboardingResponse
  PUT    /api/users/profile               REMOVED
  GET    /api/plans, /api/plans/:id       published plans only, with resolvedSets
  GET    /api/workout-logs, /:id          (writes: Phase 8)
  GET    /api/body-metrics                (writes: Phase 10)
  GET    /api/achievements                (awarded by the server: Phase 11)
  POST   /api/auth/register               + optional `timezone`
Coach (requireAuth + requireRole('coach'); :traineeId must be her trainee, else 404):
  GET    /api/coach/trainees
  GET    /api/coach/trainees/:traineeId               + onboarding answers
  GET    /api/coach/trainees/:traineeId/plans         includes drafts
  GET    /api/coach/trainees/:traineeId/workout-logs
  GET    /api/coach/trainees/:traineeId/body-metrics
