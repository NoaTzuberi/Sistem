================================================================================
1. SUMMARY
================================================================================
- Trainees can start, log, finish or discard a workout. The server creates the
  WorkoutLog at start, with sets pre-filled from the plan, and every set change is
  saved on the phone first and on the server right after. A session survives a closed
  app, a lost connection and a second device.
- The session screen: one exercise or superset open at a time, the coach's notes,
  "Last time", big one-handed steppers, ✓ per set, holds with a countdown, an optional
  rest timer, carry forward, the screen kept awake, and Finish / Discard.
- Interval mode (HIIT / Tabata): the coach marks timed exercises or a whole superset as
  Interval in the dashboard; the trainee runs it hands-free with beeps, and each work
  period logs its set. A free interval timer (/timer) logs nothing.
- Finishing notifies the coach: "<name> finished <workout>" in the dashboard bell and the
  mobile Inbox; a tap opens that trainee's Logs tab.
- Removed: the ATLAS Workout + WorkoutTemplate features (/api/workouts), the ATLAS
  ActiveWorkoutPage / WorkoutSummaryPage and their API service.

2. DECISIONS (owner answers) AND HOW THEY WERE BUILT
================================================================================
Owner answers (proposal round 1):
1. If the coach set no weight, the weight is pre-filled with her last logged weight for
   that exercise. "Last time" uses the most recent completed log containing that
   exercise. From that log it takes the heaviest working set (ties: more reps / longer
   hold); if there are no working sets, any completed set.
2. A rep range pre-fills its low end (8–12 → 8).
3. Home "Start next workout" starts or resumes in one tap. If a workout is open,
   Home's main button is "Resume workout · <title>" (also for one left open in an
   earlier week).
4. No "+ Add set". It is in the PRD §14 backlog, with "swap an exercise mid-workout".
5. WorkoutSummaryPage deleted. Until Phase 9 builds the summary, Finish opens the
   existing log screen (/workouts/logs/:id).
A. Wake lock: Screen Wake Lock API while the session (or a free timer run) is open,
   re-taken on return to the foreground, released on leave / finish / discard.
   Unsupported or refused: the screen sleeps as usual.
B. Weight step: ±1 kg for dumbbells and kettlebells, ±2.5 kg for everything else. The
   rule is in one place: apps/mobile/src/features/workouts/data/sessionConfig.ts.
C. "Last time: 40 kg × 10" is shown under the targets (see 1 for which set it uses).

Interval (proposal round 2, docs/phase-reports/phase-08-interval-proposal.md):
1. PlanExercise.interval (boolean). It is valid on timed sets only: every set has
   seconds and none has reps (draft rule, shown next to the row). In a superset, every
   exercise is Interval or none (publish rule, like the other superset rules — a draft
   can be mid-edit). The dashboard checkbox ticks the whole superset and warns about a
   mixed one.
2. A 10 s "Get ready" lead-in, which Skip skips.
3. After being away (backgrounded, locked, app closed), nothing is logged
   automatically. On return the run pauses at the current point in time and a sheet asks
   "While you were away, N work periods ended. Mark them as done?" — "Yes, I did them"
   logs those sets, "No" leaves them not done; then the run continues (or shows the end
   screen if all rounds are over). Closing the sheet counts as "No". The question is
   stored with the run, so closing the app while it is open doesn't lose it. The free
   timer logs nothing, so it never asks; it just continues from the right point.

Things I decided inside your answers (say if you want any changed):
- Server API (/api/workout-logs, trainee's own logs only; another trainee's log → 404):
    POST /                  start, or resume the same workout (201 / 200). 409
                            `other_workout_active` + the open log when another is open;
                            409 for next week's or an already done workout.
    GET  /active            her open session (any device) or null
    GET  /:id/session       log + planned workout + lastPerformance + serverTime
    PATCH /:id/sets         per-set updates; refused (409) once the log is finished
    POST /:id/finish        optional last set updates in the body; refuses 0 sets done
                            (400); stats from the server (duration, volume, sets done,
                            prCount 0 until Phase 9); emits workout.completed
    POST /:id/abandon       discard: status 'abandoned', kept but hidden from her lists
                            (and the coach's); the workout can be started fresh
  No schema change to WorkoutLog. GET /plans/week now also returns `activeLog`.
- Only this week's published workouts can be started (missed ones too, until the week
  ends — same rule as Home). One open workout at a time (the existing unique index).
- Set changes are written with one conditional update ("only while in progress"), so
  two devices editing different sets never overwrite each other, and a change that
  arrives after the workout was finished elsewhere is refused. The phone then sees that
  and leaves the screen (finished → the log page, discarded → Home).
- Carry forward: when she ticks a set, later open sets of the same exercise with the
  SAME planned target that she hasn't edited take its values. (While testing I narrowed
  this: the first version would have overwritten a planned pyramid step.)
- Focus follows her: after a ✓ it moves to the next open set after that one, wrapping
  round. (The first version jumped back to the first exercise even when she was doing
  the superset first.)
- Rest timer: after a set with a planned rest, except between exercises of a superset
  round and after the last open set. −15s / +15s / Skip; ticking the next set also ends
  it. Rest, holds and intervals count from device end timestamps (local UX); the
  workout's elapsed clock and all logged times use server time.
- Interval phases: round by round, each exercise's work then its rest (A1 → rest →
  A2 → rest …), no rest after the very last work period. Work = the set's seconds as she
  left them (the coach's target unless edited). Only sets not done yet are included, so
  a restarted interval continues where it stopped. The rows' own ▶ hold is hidden in an
  interval block; the normal rest timer doesn't run for interval sets.
- Sounds: one beep at 10 s left and at 3, 2, 1 (only when the phase is longer than that),
  and a longer, lower beep when the phase switches. Web Audio, unlocked by the Start /
  Resume tap. The mute toggle is remembered on the phone. Vibration where supported, also
  when muted.
- Free timer: defaults 20 s / 10 s × 8; work 5 s – 10 min, rest 0 – 10 min, ±5 s; rounds
  1–50. Remembers her last values. Entry: Home ("Interval timer") and the session ⋯
  menu.
- Coach notification `workout_completed` { traineeId, traineeName, logId, workoutTitle }
  goes to the trainee's coach at finish time (read from the trainee then), one per log
  (dedupeKey). describeCoachNotification now also returns `section: 'logs'`.

2b. AFTER REVIEW — SOUND FIXES
================================================================================
Bug you found: no beeps at all in desktop Chrome (Mac), in the free timer and in interval
runs.
Root cause (reproduced in Chrome before changing anything): the Start tap created the
AudioContext, then played a 10 ms silent "unlock" blip. Its fade-out was scheduled at
start + 0.01 − 0.03 = −0.02 s (a new context starts at currentTime 0). Web Audio throws
a RangeError for negative times, and the catch around it set the context to null, so
every later beep returned before scheduling anything — silently. Each later tap (Resume,
the "while you were away" answer) built a new context that failed the same way. The
context was never created outside a tap, and the tones themselves (880 Hz 0.12 s / 520 Hz
0.6 s at 0.4) were fine.
Fix (data/intervalSounds.ts):
  - every scheduled time is ≥ the start time, whatever the tone length;
  - the context is kept even if the unlock step fails;
  - the unlock uses the standard empty buffer, not a tone;
  - a beep resumes a context that was suspended again (e.g. by the OS);
  - any tap on the interval screen re-enables sound — a run restored after reopening the
    app had no Start tap, so it stayed silent until Pause / Resume.
Dev only: a "Test sound (dev)" button on the free timer setup (the 10 s beep, then the
final beep), and each beep logs `[intervalSounds] beep <kind> — AudioContext: <state>`
via console.debug (Chrome's "Verbose" level). Neither is in production builds.

Hold beeps (your request): the ▶ countdown on timed sets (plank ▶ 45s) now uses the same
pattern — one beep at 10 s left (skipped when the hold is 10 s or shorter), 3-2-1, a
longer beep at 0 (with vibration where supported). The rule (`isCountdownBeep`) and the
mute setting (`isSoundMuted` / `setSoundMuted`) moved into the shared sound module, so
holds, interval runs and the free timer share one pattern and one mute (toggled on the
interval screen). The ▶ tap unlocks audio.
(The rest timer between sets got the same beeps afterwards — §2d.)

Checked in Chrome (desktop):

  - Hold on your open "Workout 2" session (3/4 sit-up, set 3): 12 s → beeps at 10 s

2c. AFTER REVIEW — SMOOTH COUNTDOWN BARS
================================================================================
Bug you found: the interval run's progress line moved in visible jumps.
Cause: the line was a <progress> element whose value was React state, redrawn only on
the hook's timer tick (every 100 ms for the interval run, every 250 ms for the rest bar;
slower whenever the browser throttles timers). Each redraw was a step, and <progress>
repaints with layout.
Fix: one CountdownBar component (features/workouts/components/CountdownBar):
  - every animation frame (requestAnimationFrame) it reads the stored phase end
    timestamp and sets transform: scaleX() on the fill (transform-origin left) — GPU
    only, no layout, linear by construction (no transition, no easing). React re-renders
    never move it.
  - Paused: drawn once from the frozen time left, and no frame loop runs. Resume continues
    from exactly there, because the new end time = now + the time left.
  - Skip / next phase: the new end time and length are drawn at once from the left —
    never animated backwards.
  - prefers-reduced-motion: the same loop, but the value only changes in whole seconds.
  - The big number still updates once per second.
  Used by the interval run (fills up) and the free timer (the same screen), and by the
  rest bar (drains). The hold countdown has no bar (only its "0:32 · Stop" label), and
  the sets-done bar in the session header is not a countdown — both unchanged.
  The fill's transform is set from code, like dnd-kit's drag position on the dashboard
  (commented as the one inline-style exception).

Checked in Chrome: my test window reports itself as hidden, so Chrome runs no animation
frames there (0 fps). I replaced requestAnimationFrame with a queue that I flushed at
measured times, reading the bar's scaleX after each frame (free timer, your 30 s / 15 s
× 8 settings):
  - Every 100 ms frame moved the bar by exactly +0.00333 (1/300 of a 30 s phase); one
    frame loop running.
  - A full work phase (30 s) and the following rest (15 s), sampled about once a second:
    linear throughout (+0.030 and +0.060 per 0.9 s). At the work → rest switch the bar
    started again from the left at once; the number stepped once per second.
  - Pause mid-phase: frozen at 0.1505 for 2.8 s, no frame loop running. Resume: 0.1572
    after 200 ms — continued from exactly where it stopped.
  - Skip: reset to 0 at once.
  - Reduced motion: whole-second steps only (1/15 per second in a 15 s rest).
  - Not watched with real frames (needs a visible window — please watch one run), and the
    session rest bar wasn't run in the browser (it would need a set ticked in your open
    session); it uses the same component.
  - Your free-timer settings are unchanged; my test run was stopped and cleared.
